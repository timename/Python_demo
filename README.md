## 第 1 周 · 诗词字数统计器（`read_plus.py`）

**目标**：练习文件读写、异常处理、字典计数、排序。

**功能**：读取 `poem.txt`，统计每个汉字出现次数，按次数降序输出前 10 名到 `result.txt`。

**运行**：

```bash
python read_plus.py
```

**涉及的知识点**：

| 知识点 | 用法 |
|---|---|
| `try / except FileNotFoundError` | 文件不存在时返回 `None`，不崩溃 |
| `with open(..., encoding="utf-8")` | 自动关闭文件，正确处理中文 |
| `dict.get(key, 0) + 1` | 字典计数，避免 KeyError |
| `sorted(..., key=lambda x: x[1], reverse=True)` | 按值降序排序 |
| `list[:n]` | 切片取前 n 个 |
| Unicode 范围判断 | `'\u4e00' <= char <= '\u9fff'` 只识别汉字 |

**踩过的坑**：

1. **字典 `+= 1` 报 KeyError** —— Python 字典访问不存在的 key 会抛异常，不会自动初始化为 0，必须用 `.get(key, 0)`。
2. **黑名单不可靠** —— 最初用「排除标点」的方案，结果漏掉了半角逗号 `,`，导致逗号排到第 1 名。改为白名单（只认汉字 Unicode 区间）后解决。
   > 结论：排除法永远补不全，只保留目标字符才可靠。
3. **函数漏写 `return`** —— `count_chars` 忘记返回，导致下游拿到 `None`，报 `AttributeError: 'NoneType' object has no attribute 'items'`。

**输出示例**：

```
——《诗词》字数统计——
总计：27 字（不含标点）

前 10 名：
1. 我  1 次
2. 欲  1 次
...
```

## 第 2 周 · 手写工具调用循环（`week02_llm/tool_calling.py`）

**目标**：不用任何框架（LangChain 等），从零实现一个 Agent 的工具调用内核。

**核心认知**：

> 模型只会输出文本，不会执行任何东西。
> "调用工具" = 模型输出一段结构化文本 + **你的代码**去执行 + 把结果发回去。

模型是「大脑」，你的代码是「手脚」。所谓 Agent，就是这两者的循环协作。

**运行**：

```bash
python week02_llm/tool_calling.py
```

**实现流程**：

```
用户提问 → 发给模型（附工具定义）
            ↓
      模型返回 {"tool": "xxx", "args": {...}}
            ↓
      你的代码查表 → 执行真正的函数 → 拿到结果
            ↓
      把「工具调用记录」+「执行结果」追加进历史
            ↓
      把完整历史再发给模型 → 模型给出最终答案
```

**关键实现点**：

| 知识点 | 说明 |
|---|---|
| **对话历史重放** | 模型没有记忆，每轮必须把完整历史重新发过去 |
| `TOOL_IMPL` 注册表 | 「工具名 → 函数」的映射，把模型的字符串请求翻译成真实调用 |
| `call_id` 配对 | 模型可一次请求多个工具，靠 `call_id` 把结果和请求对应上 |
| `max_rounds` 兜底 | 防止工具反复失败导致无限循环 |
| **指数退避重试** | DNS 失败 / 超时自动重试（2s、4s 递增），4xx 不重试 |

### 实验：模型到底会不会算数？

同一道题 `987654 × 321098`，让模型直接算，`temperature=0` 连问 3 次：

| 次数 | 模型回答 | 正确答案 |
|---|---|---|
| 1 | 317102934892 | 317133724092 |
| 2 | 317113330092 | 317133724092 |
| 3 | 317112968892 | 317133724092 |

**3 次给了 3 个不同答案，全部错误。**

答案都以 `3171` 开头、都是 12 位——它学会了「大致形状」，但具体每一位在猜。

**这证明了**：模型不是在计算，是在**按文本模式补全**。给它 `calculator` 工具后，同一题得到正确答案。

> 结论：模型的能力边界在「知道该调什么」，而不在「执行」。

### 验证过的四种异常场景

| 场景 | 现象 | 学到什么 |
|---|---|---|
| 正常调用 | 算出正确结果 | 完整闭环 |
| 模型拒绝不存在的工具 | 明确说明限制 | 模型能读工具列表 |
| **工具存在但无实现** | 报错 → 模型改用内部知识 | **错误信息要写清楚，模型会用它** |
| 工具返回 `None` | 循环 5 轮后强制停止 | **必须有最大轮数兜底** |

### 踩过的坑

1. **无限重试** —— `result = None` 时，模型收到「调用了但没结果」，会不断重试直到达到上限。工具失败时必须返回**有意义的错误信息**，而不是 `None`。
2. **工具定义前后矛盾** —— 只改了 `name` 没改 `description`，模型如实报告「translate 工具是用来算数学的」。**`description` 才是模型判断「要不要用」的依据**，名字只是标识符。
3. **DNS 解析偶发失败** —— `getaddrinfo failed`，网络抖动导致。加了重试机制解决，并区分 4xx（不重试）与 5xx/网络错误（重试）。

## 第 3 周 · RAG 全链路（`week03_rag/`）

**目标**：不用向量库，从零实现 RAG，让模型基于私有文档回答，而不是靠记忆瞎编。

### 为什么需要 RAG

模型没训练过你的体检报告。没有 RAG 时有两种坏结果：

```
你：我去年血糖多少？
模型：我没有你的健康数据。            ← 拒答
模型：您的血糖是 5.2 mmol/L。          ← 更糟：编造
```

RAG 的做法：**先从你的资料里检索出相关段落，塞进提示词，让模型"照着答"。**

### 五步链路

```
① 文档切分   chunk_report()   按语义小节切，不按固定字数切
② 建索引     build_index()    每个 chunk 建词频表
③ 检索       retrieve()       算相关度，取 top 3
④ 拼接       build_prompt()   把检索结果拼成"参考资料"
⑤ 生成       call_model()     模型基于参考资料回答
```

### 文件说明

| 文件 | 说明 |
|---|---|
| `rag.py` | 朴素 TF-IDF 版本（基线） |
| `rag_length.py` | BM25 版本（含长度归一化 + tf 饱和），并内置两版对比 |

运行：

```bash
python week03_rag/rag.py                          # 基线版
python week03_rag/rag_length.py --no-llm          # 只对比检索，不调模型（省钱）
python week03_rag/rag_length.py                   # 完整对比 + 模型回答
python week03_rag/rag_length.py --question "血糖怎么样"
```

### 核心算法：从 TF-IDF 到 BM25

**朴素 TF-IDF**

```
score = Σ (tf_in_chunk × idf_of_token)
```

- `tf`：这个词在这个块里出现几次
- `idf`：这个词有多独特（出现得越多越低）

**为什么是乘不是加**：`tf` 回答"这个块和问题多相关"，`idf` 回答"这个词值不值得关注"。相乘才等于"这个块里有多少值得关注的词"。

**BM25 补上了 TF-IDF 的两个缺陷**

| 缺陷 | 后果 | BM25 的解法 |
|---|---|---|
| 长块天然占优 | 字数多 → 什么词都可能碰巧出现 → 分数虚高 | **长度归一化**：块越长，分数打折越多 |
| tf 无上限 | 出现 100 次比出现 10 次强 10 倍 | **tf 饱和**：边际递减，10 次以后几乎不再涨 |

```
tf_norm = (tf × (k1 + 1)) / (tf + k1 × length_penalty)
length_penalty = (1 - b) + b × (块长度 / 平均长度)

k1 = 1.2   控制 tf 饱和速度
b  = 0.75  控制长度惩罚强度（标准经验值）
```

### 对比实验数据

同一份报告、同一批问题，两版算法的检索排序：

| 问题 | 朴素 TF-IDF | BM25 | 变化 |
|---|---|---|---|
| 我的血糖怎么样？ | 四、总结 **6.53** > 3.血糖与血脂 5.38 | **3.血糖与血脂 5.63** > 四、总结 5.21 | ✅ 排序修正 |
| 肝功能有没有问题？ | 四、总结 **11.60** > 2.肝功能 5.65 | 四、总结 7.21 ≈ 2.肝功能 7.00 | ⚠️ 差距从 2.1 倍缩到 1.03 倍 |
| 医生建议我做什么？ | 四、总结 14.31 | 四、总结 10.50 | ✅ 正确保持第 1 |
| 我的血型是什么？ | 四、总结 **3.18**（误命中） | **检索到 0 个片段** | ✅ 噪声完全消除 |

**关键观察**：

- 长块（190 字）分数被压低 ~38%（11.60 → 7.21），短块（36 字）几乎不变（5.65 → 7.00）——**这就是长度归一化在起作用**。
- 「血型」问题下，BM25 把所有块压到 `MIN_SCORE` 以下，直接返回空——**不喂垃圾给模型，模型才能诚实说"未提及"**。
- 肝功能题排序未翻转，因为「四、总结」本身就涵盖所有话题。但两块的分数已接近，且都进了 top-2，**模型仍能拿到精确数值**——这是 top_k 冗余的价值。

### 防幻觉的三道闸门

1. **`MIN_SCORE` 阈值**：分数太低直接过滤，不塞给模型
2. **Prompt 约束**：明确"只能用参考资料回答，没有就说'报告中未提及'"
3. **要求标注来源**：`[来源：小节名]`，强制模型对齐原文

实测结果：问「我的血型是什么？」→ 检索 0 个片段 → 模型回答「报告中未提及。」✅

### 踩过的坑

1. **切分把列表项当成章节标题** —— `1. 体重超重，BMI偏高；` 被 `^\d+\.` 误判为小节，导致一个 chunk 吞掉整段建议，块长达 257 字，在所有问题上都排第一。
   - 尝试过用 `len < 15` 限制，仍会误判
   - 最终改用**结尾标点判断**：以「；」「。」「，」结尾的，是列表项不是标题
   > 结论：RAG 的效果 70% 取决于切分质量，30% 才取决于检索算法。

2. **长块占优导致排序错误** —— 修正切分后仍有问题，才发现是「没有长度归一化」。这促成了 BM25 那一版。

3. **`MIN_SCORE` 设成 0.0 太宽松** —— 完全无关的问题也能检索到 3 个片段（3-6 分），模型虽然后来靠 Prompt 兜住了，但那是运气好。提高到 3.0 后，噪声被正确过滤。

### 与向量检索的对比

本项目用的是关键词检索（BM25），因为 API 中转站不提供 embedding 接口。两者的取舍：

| | BM25 | 向量检索 |
|---|---|---|
| 精确词匹配 | ✅ 强 | ⚠️ 一般 |
| 同义词理解 | ❌ 不懂 | ✅ 强 |
| 可解释性 | ✅ 能说清每分怎么来的 | ❌ 黑盒 |
| 依赖外部模型 | ❌ 不需要 | ✅ 需要 |
| 速度 | ✅ 极快 | ⚠️ 较慢 |

**生产系统常用混合检索**：两路都跑，结果融合。医学报告这类场景，关键词检索其实更准——「血糖」就是「血糖」，不需要语义泛化。

## 第 4 周 · 体检报告智能助手（`week04_project/`）

**目标**：把前两周的 Agent 与 RAG 合成一个完整可用的系统，加上 trace 日志与测试用例。

### 架构

```
用户提问
   ↓
Agent 主循环（模型决定调哪个工具）
   ├─ search_report    BM25 检索（复用第 3 周）
   ├─ get_indicator    按指标名精确取值
   ├─ list_abnormal    列出所有异常指标
   └─ calculate_bmi    按身高体重算 BMI
   ↓
最终答案 + trace 日志（JSON，可回放）
```

### 文件说明

| 文件 | 职责 |
|---|---|
| `retrieval.py` | BM25 检索（从 week03 抽取成可复用模块） |
| `tools.py` | 4 个工具的实现 + 给模型看的 schema + 注册表 |
| `agent.py` | 主循环、trace 记录、测试用例 |
| `selftest.py` | 不调模型的模块自测（验证工具能独立工作） |
| `data/report.txt` | 体检报告语料 |
| `traces/` | 运行时生成的 trace JSON（已 gitignore） |

运行：

```bash
python selftest.py                                  # 工具自测，不花钱
python agent.py                                     # 跑 6 个测试用例
python agent.py --question "血糖是多少" --trace      # 单问 + 保存 trace
```

### 6 个测试用例的结果

| # | 问题 | 期望 | 实际 |
|---|---|---|---|
| 1 | 我的血糖是多少？ | 答出 7.2 | ✅ get_indicator → 7.2 偏高 |
| 2 | 肝功能有问题吗？ | ALT 55 偏高 | ✅ 多工具协同 |
| 3 | 有哪些异常指标？ | 列出异常项 | ✅ list_abnormal → 表格 |
| 4 | 身高172体重78算BMI | calculate_bmi | ✅ 26.4 超重 |
| 5 | 报告里的医生是谁？ | 王医生 | ✅ search_report |
| 6 | 我的血型是什么？ | 未提及 | ✅ **两次尝试后诚实拒答** |

**用例 6 是最有价值的一次**：模型先调 `get_indicator("血型")` 失败，又换 `search_report("血型 ABO Rh")` 再失败，第三次才回答「未提及，建议单独做血型鉴定」。

**它没有一次失败就放弃，也没有编造答案。**

### Trace 日志

每次对话都记录完整步骤，示例：

```json
{
  "question": "我的血糖是多少？",
  "timestamp": "2026-11-07T10:18:29",
  "steps": 2,
  "trace": [
    {"round": 1, "type": "tool_call", "tool": "get_indicator",
     "args": {"name": "血糖"}, "result": "空腹血糖(GLU)：7.2 ...", "elapsed_ms": 0},
    {"round": 2, "type": "text", "text": "你的空腹血糖是 7.2 mmol/L ..."}
  ]
}
```

**为什么 trace 重要**：用户说「答错了」时，能精确定位是**模型选错工具**、**参数给错**、还是**工具返回错数据**。没有 trace 只能靠猜。

### 踩过的坑

**1. 系统代理导致 SSL 连接被断**

报错：
```
SSL: UNEXPECTED_EOF_WHILE_READING  (固定 5 秒后失败)
```

排查过程：
- DNS 正常、TLS 握手成功（TLSv1.3）
- 手工 socket 发请求 → **HTTP 200 成功**
- `http.client` → **成功**
- `urllib` → **全部失败**
- Node 的 fetch → **成功**

根因：`urllib` 会读 Windows 系统代理（`127.0.0.1:7897`，Clash 默认端口），而该代理在转发到本 API 时会中断连接。Node 的 fetch 默认不读系统代理，所以不受影响。

修复：
```python
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
with opener.open(req, timeout=60) as resp:
    ...
```

> 教训：`urllib` 的「贴心」有时是陷阱。排查 HTTP 问题的顺序应当是：先确认网络层（DNS/TLS），再确认应用层（手工 socket），最后才怀疑代码。

**2. Agent 路径不可复现**

同样的 `temperature=0`，同样的 6 个用例，两次运行的工具调用序列不同：

| 用例 | 第一次 | 第二次 |
|---|---|---|
| 肝功能 | `get_indicator ×2 + search_report` | `search_report + list_abnormal` |

原因：多轮对话中每一轮的上下文不同，模型的选择会漂移。

**这是 Agent 测试的核心难点**——答案可以一致，但路径不保证一致。因此评估标准应该是「**最终答案是否正确**」，而不是「是否按预期路径执行」。

**3. `list_abnormal` 只覆盖一半异常项**

工具只返回带 `[偏高 ↑]` 标记的 4 个生化指标，但报告总结里列了 5 条异常（含「体重超重」「血压偏高」这些没有标记的文字描述）。

模型照搬了工具的返回，说「共 4 项异常」。

> **工具的边界就是 Agent 的边界。** 工具看不到的东西，Agent 答不出来。改进方向是让 Agent 同时调 `list_abnormal` 和 `search_report("异常提示")`，但这又需要在 Prompt 里明确告诉它「这个工具不全」。

### 与「AI 调试」岗的对应关系

| JD 要求 | 本项目对应 |
|---|---|
| 排查输出幻觉 | 用例 6：工具查不到时必须拒答 |
| 逻辑校验 | trace 中可看到每步的工具与参数 |
| 异常排查 | 三种错误处理：工具不存在、参数错误、返回值非法 |
| 输出调试报告 | `traces/*.json` 完整的「现象→步骤→结果」 |
| 测试用例设计 | 6 个用例覆盖正常/边界/不存在三类 |
